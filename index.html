Episode 01

Trust chains in five minutes

A TLS client trusts a server certificate only if it can build a chain from that certificate up to a root in its trust store. Roots rarely sign server certificates directly. They sign intermediate CAs, and intermediates sign the leaf certificates that websites present. Every intermediate inherits the full trust of its root, for any domain name, unless a constraint says otherwise.

That inheritance is the whole story here. Steal or guess an intermediate’s private key and you can mint a certificate for yourbank.com that chains to a trusted root.

Two details make cleanup harder. Sectigo had cross-signed all eight keys under its own root, so the same keys chain to two independent roots. And on Windows, eMudhra’s TLS and code-signing G3 roots are trusted directly. Removing one root from one trust store does not close every path.

★ Key idea

Browsers moved within five hours because they own a push channel for distrust. Most other software has no such channel, and a fix there means a package release, an image rebuild, or a firmware update.

Episode 03

The weak keys

These are ECDSA keys on the NIST P-384 curve. The private key is a scalar d, and the public key in the certificate is the point Q = d·G, where G is the curve’s fixed generator. Security rests on d being a uniformly random number of about 384 bits. Each of these eight was an integer below 256: roughly 8 bits of entropy. Recovering one means computing G, 2G, 3G, … until a point equals Q, at most 255 steps.

A correctly generated P-384 key is not the weak point in any realistic threat model. A badly generated one is.

Episode 04

How a ceremony goes wrong

A key ceremony is the scripted, witnessed, audited procedure in which a CA generates keys inside a hardware security module (HSM) and produces certificate signing requests. eMudhra’s preliminary report in Mozilla bug 2083449 describes this chain of failures:

  1. A faulty ceremony script created a second, weak key pair on the HSM alongside each properly generated one.
  2. Labels looked alike. Staff selected keys by human-readable label, and the weak pairs were picked when building the CSRs.
  3. The certificates were issued over the weak public keys, so the certified key and the key the CA actually signed with later were not the same.
  4. Human error at several steps, by eMudhra’s own account, let it pass review and audit.
★ The missed signal

If the CA kept signing CRLs with the good HSM key while the certificate carried the weak public key, every CRL signature would fail to verify. That is exactly what was observed in May–June 2025. The June bug was closed as a process slip, and eMudhra now links those invalid signatures to the same key mismatch. A pairwise-consistency check failed in production, publicly, 16 months before anyone looked closer.

eMudhra says only one of the eight (EM DV TLS CA – G3C) was ever put into production and that none issued end-entity certificates. It has stopped issuing from the G3 hierarchy and plans to re-verify every ceremony it has performed. Because root programs are distrusting the root, about 30,000 customer certificates need to move to another hierarchy.

Episode 05

Blast radius

This is unusual among CA compromises. Normally someone steals a key, and you can reason about when it happened and who has it. Here nobody had to steal anything: the key was derivable from the public certificate from the day it was issued. Assume all eight keys are known to every attacker.

TLS impersonation

Six keys can sign a server certificate for any domain. An on-path attacker can intercept or modify HTTPS traffic for any client that accepts the chain.

Client auth and mTLS

At least one intermediate carries the Client Auth EKU, so forged client certificates are possible against servers that authenticate clients through these roots.

Code signing

Two keys chain to a code-signing root trusted by Microsoft. Signed malware could look like it came from a verified publisher on systems that skip revocation checks.

Exposure window

About 17 months (April 2025 to October 2026). No exploitation has been confirmed, and nothing can prove the keys were never used against clients that ignore CT.

★ What CT proves, and what it doesn’t

No certificate chaining to these intermediates appears in Certificate Transparency logs before the block. Chrome, Firefox, Safari and Edge refuse publicly trusted TLS certificates without CT proofs, so they could not have been attacked. curl, Python, Node.js, Go services and IoT firmware don’t enforce CT, and for them the logs say nothing. Code-signing certificates aren’t logged at all.

Episode 06

Browsers vs. everything else

A browser rejecting one of these certificates now does so three ways at once. Most other TLS stacks have none of these defenses and rely on a static root bundle.

Firefox · OneCRL / CRLite

Pushed intermediate blocklist

Delivered through remote settings, no update or restart. Firefox 158.0.1 and the ESRs carry it for installs that disable remote settings.

Chrome · CRLSets

Pushed revocation set

Shipped 1 h 40 m after the report. Chrome didn’t need to block the code-signing keys, since its TLS verifier won’t build a path through a code-signing-only intermediate.

All major browsers · CT

Transparency enforcement

A forged leaf has no SCTs, and Google worked to ensure logs refuse certificates from these CAs.

Root programs

Distrust the root

Mozilla removed emSign ECC Root CA – G3 in NSS 3.131.1. Chrome is removing it too and reviewing eMudhra’s remaining roots.

Where the gap is

  • Bundled CA files. curl, Python (certifi, pip, uv), Node.js and Rust (webpki-roots) carry their own copy of the Mozilla roots and usually don’t check revocation. In Scott Helme’s tests, curl, Python and Node.js on Linux and macOS accepted a forged certificate from EM DV TLS CA – G3B.
  • Static binaries. Go embeds its fallback roots and the new block at compile time. Deployed Go binaries keep the old behaviour until rebuilt with Go 1.27.3 or 1.26.10. The same applies to Electron apps.
  • Containers. A running image keeps the ca-certificates it was built with. Rebuild from a patched base.
  • macOS command-line tools. The built-in curl, git, python3 and openssl read /etc/ssl/cert.pem, which wasn’t updated, and don’t consult the OS block.
  • Embedded and IoT devices with frozen trust stores. These need the intermediates distrusted by hand, segmentation, and outbound restrictions.
★ Why “remove the root” is not enough

Removing emSign ECC Root CA – G3 still leaves the Sectigo cross-signs chaining the same keys to AAA Certificate Services, and Windows trusts the eMudhra TLS and code-signing G3 roots directly. Debian removed both emSign ECC Root CA – G3 and AAA Certificate Services. Removing AAA can break legitimate sites, so it needs testing before broad rollout.

Episode 07

Lab: is your client exposed?

The community disclosure site runs test hosts that serve chains through the compromised intermediates. For these checks a certificate error is the good result.

Task 1 · Probe your command-line clients

shell
curl https://dv-g3b-emudhra.we-have-a-problem.com/
curl https://dv-g3b-aaa-emudhra.we-have-a-problem.com/
# error  → client rejects the intermediates (good)
# a page → this client still trusts them; update its trust store

The second host serves the Sectigo cross-signed path. Run both from your laptop, a CI runner and a container, and compare.

Task 2 · Check the bundle your language uses

shell
python3 -c "import certifi; print(certifi.__version__)"   # want ≥ 2026.10.19
node -p "process.versions.node"                            # 22.23.4 / 24.22.1 / 26.12.1
go version                                                 # ≥ 1.27.3 or 1.26.10, then rebuild
grep -E 'emSign_ECC|Comodo_AAA' /etc/ca-certificates.conf   # Debian/Ubuntu: '!' = distrusted

Task 3 · Verify the reporter’s proof

The disclosure site’s proof.zip holds each certificate, its public key, and a signature over the reporter’s message. Confirm that the signing key matches the certified key:

shell
openssl x509 -in EM-DV-TLS-CA-G3B.crt.pem -noout -pubkey | diff - EM-DV-TLS-CA-G3B.pub.pem
openssl dgst -sha384 -verify EM-DV-TLS-CA-G3B.pub.pem \
  -signature EM-DV-TLS-CA-G3B.sig message.txt

Task 4 · Write the check the ceremony was missing

Given any EC CA certificate, test whether its key is a small scalar. This takes a few seconds for 216 candidates and would have caught all eight keys on day one.

python · weak_key_check.py
import sys
from cryptography import x509
from cryptography.hazmat.primitives.asymmetric import ec

cert = x509.load_pem_x509_certificate(open(sys.argv[1], "rb").read())
pub = cert.public_key().public_numbers()
curve = cert.public_key().curve

for d in range(1, 1 << 16):
    q = ec.derive_private_key(d, curve).public_key().public_numbers()
    if (q.x, q.y) == (pub.x, pub.y):
        print(f"WEAK KEY: d = {d}  ({cert.subject.rfc4514_string()})")
        break
else:
    print("no small scalar found")

Extension: rewrite it with incremental point addition (Qk+1 = Qk + G) instead of a fresh scalar multiplication each step, and measure the speed-up.

Episode 08

Lessons and discussion

For anyone who runs keys

  • Pairwise consistency, every time. Before publishing a certificate, sign a test value with the exact HSM key handle you will use and verify it with the certificate’s public key.
  • Select keys by fingerprint, not by label. Bind CSRs to a key identifier (SKI or public-key hash) that the ceremony record checks, not to a name a person reads off a screen.
  • Lint keys, not only certificates. Small-scalar, duplicate-key and known-weak-generator tests are cheap and belong in ceremony scripts and in CA monitoring.
  • Treat “wrong key” symptoms as security events. An invalid CRL signature from a CA is a key-integrity question first and a process question second.

For anyone who relies on keys

  • Know every trust store you ship. OS bundle, language bundle, the copy inside a static binary, the one baked into a container image or firmware.
  • Have a distrust path faster than a release. Browsers have OneCRL and CRLSets; most backends have nothing between “root trusted” and “next package update.”
  • Enforce CT where you can. It turned an unknowable exposure into a provable non-event for browser users.

Discussion questions

Why did Chrome block only six of the eight intermediates?

The other two are restricted to code signing. Chrome’s TLS path builder won’t accept a code-signing-only intermediate in a server chain, so those keys couldn’t produce a certificate Chrome would trust for HTTPS.

Mozilla removed emSign ECC Root CA – G3. Why can a client with that update still be at risk?

The Sectigo cross-signs chain the same eight keys to AAA Certificate Services. A client that trusts AAA, doesn’t check revocation, and lacks an intermediate blocklist can still build a valid path.

What lets us say browser users were never attacked, and why doesn’t that extend to curl?

CT logs show no certificate under these intermediates before the block, and browsers require CT proofs. curl and most libraries don’t check SCTs, so a forged certificate never logged anywhere would still be accepted.

How could the June 2025 CRL incident have exposed this 16 months earlier?

Ask why the CRL signature didn’t verify against the certificate’s key. Recovering or comparing the certified public key with the HSM signing key would have shown a mismatch, and a small-scalar test on the certified key would have found d immediately.

This incident has no CVE of its own, yet many products shipped “security fixes.” Is CVE the right tool for trust-store changes?

Open question. Points for: scanners and SBOM tooling key off CVE IDs. Points against: one CA event spawned per-ecosystem IDs (Go, Firefox) that describe the same root cause differently.

Should a root program distrust a whole hierarchy for a mistake in eight intermediates that issued no customer certificates?

Weigh 30,000 certificates to migrate against the signal that a CA’s ceremony, audits and incident response all missed a key that was guessable for 17 months, after a public warning sign.
