0.1The answer formula

The course repeats one line: there is no universal “best WSN protocol”. So an answer that only names a winner is weak. A strong design answer names four things:

design claim = mechanism + what it saves + where the cost moves + conditions (traffic, topology, links)

Weak: “ContikiMAC is energy efficient.” Strong: “ContikiMAC cuts receiver idle listening to roughly T_check / T_w by having the sender repeat the data frame until an ACK arrives. The cost moves to sender airtime and about T_w / 2 rendezvous delay per hop, which is fine for rare unicast and expensive for broadcast.”

For lab questions, use the lab rule from Week 1: a simulation screenshot is not a result; an interpreted measurement is a result. Report the configuration (mote type, radio medium, RDC/MAC, packet interval, duration), the measurement (counts, PRR, ticks), and what changed and why.

Week 1 · lecture + lab

1 · WSN & mote hardware

Week 1 mindset: a sensor network is not a normal network made smaller. It is computation attached to a physical environment.

1.1What a WSN is

A WSN is a set of spatially distributed embedded nodes that sense, process and communicate wirelessly. Nodes are called sensor nodes or motes. A sink, gateway or border router collects data and connects the WSN to users or other networks. Traffic is mostly small, periodic or event-driven, and strongly constrained by energy. Think of a WSN as measurement infrastructure, not as general-purpose mobile devices.

TermFocus
WSNSensing and wireless embedded networking; often the field layer where measurements are born
IoTConnecting physical devices to Internet services and applications
Cyber-physical systemDigital computation monitors or controls a physical process

A WSN may be part of an IoT or CPS architecture, but it can also operate locally. Reference architecture: sensor nodes → multi-hop forwarding → gateway / sink → application / cloud. The gateway is the translation point between constrained wireless networking and ordinary computing infrastructure.

The path of one measurement

  1. A sensor samples a physical quantity.
  2. The microcontroller converts, filters or formats the value.
  3. The radio sends a small frame to a neighbour or gateway.
  4. Intermediate motes may forward or aggregate it.
  5. The sink exports it to a database, dashboard or controller.

Every step has an energy, delay, reliability and security cost.

1.2The six constraints

WSN design is multi-objective: improving one dimension often hurts another.

1 · EnergyRadio can dominate, especially through idle listening. Battery replacement may be impossible, dangerous, or cost more than the node. Sleeping saves energy but adds latency and rendezvous complexity.A mote that never wakes has excellent lifetime and zero usefulness. T3
2 · Memory & CPURAM holds packet buffers, routing tables, stacks, queues, state. Code must fit program memory. Crypto, routing and logging are not free. Prefer compact state machines.“Where does this state live?”

1.4Mote hardware anatomy

A mote is not “a sensor”; it is a constrained networked computer with sensors attached. Data flow: Sensors → ADC → MCU → Radio → Antenna, with Memory and Power beside the MCU. Sensors create raw evidence; the MCU decides when and what to transmit; the radio and power subsystem dominate lifetime questions.

2 · Radio & PHY

Anchor: a wireless link is not a cable; it is a probability distribution with packets attached T1. Routing, MAC scheduling and energy models go wrong if PHY assumptions are too clean.

2.1dBm, dB and the link budget

  • dBm = absolute power relative to 1 mW (received signal = −85 dBm). dB = a ratio, gain or loss (path loss = 70 dB, antenna gain = 2 dB).
  • +3 dB ≈ ×2 power, +10 dB = ×10, −10 dB = ÷10.
  • Negative dBm is normal (less than 1 mW). −80 dBm is stronger than −90 dBm; “larger” means less negative. Do not drop the minus sign.
P_r = P_t + G_t + G_r − PL − L_s (dBm, dB, dB, dB, dB)

Example: P_t = 0 dBm, antennas 0 dB, PL = 75 dB, L_s = 2 dB → P_r = −77 dBm. Then ask: is that above sensitivity, and where is the noise floor?

  • Receiver sensitivity is not a cliff T5. It is the minimum signal level for a given performance target. Delivery probability falls gradually as the signal weakens; links are not perfect above it and impossible below it.
  • Noise floor and SNR: SNR_dB = P_signal,dBm − P_noise,dBm. Signal −80 / noise −100 → SNR 20 dB (likely good). Signal −80 / noise −82 → SNR 2 dB (likely poor). The same RSSI can behave differently.

2.2Propagation: path loss, shadowing, fading

Keep the three effects distinct:

EffectScaleCause
Path lossAverage trend with distanceGeometric spreading, absorption, reflection, diffraction, scattering, penetration, antenna/polarization
ShadowingSlow, large-scale deviation around the trendObstacles: concrete wall, metal cabinet, human body, vegetation, machinery, vehicles
FadingShorter-term variationMultipath: copies with different amplitude, phase, delay, direction combine
Free space: PL_FS(d) = 20 log₁₀(4πd / λ), λ = c / f 2.4 GHz: λ ≈ 0.125 m → PL ≈ 40 dB at 1 m, 60 dB at 10 m

Free space: ×10 distance → +20 dB. Useful reference, too clean for indoor WSNs.

Log-distance: PL(d) = PL(d₀) + 10 n log₁₀(d / d₀) n = 2 free space, larger indoors

Example: PL(1 m) = 40 dB, n = 3, at 10 m → 40 + 30·1 = 70 dB, i.e. 10 dB more than free space at the same distance. Estimate n by measurement.

Log-normal shadowing: PL(d) = PL(d₀) + 10 n log₁₀(d / d₀) + X_σ

The deterministic term gives the average; X_σ is random variation from environment structure. Larger σ = stronger variability (“same distance, different received power”).

  • Multipath: same-phase components reinforce (constructive), opposite-phase components cancel (destructive). At 2.4 GHz, λ ≈ 12.5 cm, so moving a mote a few cm can matter.
  • Slow vs fast fading: channel changes slowly vs significantly relative to packet time. Static nodes still fade, because people, doors, vehicles and machines move.
  • Flat vs frequency-selective: all frequency components affected equally (amplitude changes, shape kept) vs differently (waveform distortion). Depends on bandwidth and multipath delay spread.
Combined: P_r(d,t) = P_r(d₀) − 10 n log₁₀(d / d₀) − X_σ + F(t)

Received power is not a deterministic function of distance. Two equal-length links can behave differently (wall material, orientation, height, metal, bodies, interference, multipath). Use measurement, not geometry alone T1.

2.4Transitional region, hysteresis, asymmetry

  • Why the transitional region hurts: a node appears as a neighbour, then disappears; broadcasts work but ACKs fail; one channel works and another does not; routing keeps selecting and removing it; retransmissions waste energy. “Almost works” is often more expensive than clearly bad. Shortest geographic link ≠ lowest-energy link.
  • Hysteresis: one threshold causes rapid add/remove flapping when PRR hovers around it. Two thresholds (add if PRR > 0.8; keep until PRR < 0.5) create a stability band.
  • Asymmetry: A→B PRR = 0.95 while B→A = 0.40. Causes: different TX power, receiver sensitivity variation, antenna orientation, different local noise floor, interference near one receiver, temporary fading.
P_success = PRR_forward × PRR_reverse 0.90 × 0.50 = 0.45

A strong data direction is not enough if ACKs cannot return. A node may hear a parent’s advertisements, select it, then fail to deliver in the reverse direction the protocol needs.

2.5IEEE 802.15.4 PHY

IEEE 802.15.4 defines the PHY and MAC for low-rate, energy-constrained wireless. IEEE 802.15.4 ≠ Zigbee T7: Zigbee adds network, application support and profiles above it; other stacks (6LoWPAN, WirelessHART, ISA100.11a) also use 802.15.4.

Week 3 · lecture + energy lab

3 · Energy

Core thesis: a WSN is useful only if it performs its sensing task sustainably under a strict energy budget. Sustainable service = required sensing + required communication + acceptable lifetime. Energy shapes application behaviour (sampling, local processing), communication (when the radio wakes, retries, control rate) and network behaviour (who forwards, path balance, repair).

Energy-aware design is state-aware design: how long was the CPU active, the radio listening, the radio transmitting, a sensor on? Which current goes with each state, at what voltage? Were transitions or uninstrumented peripherals ignored?

A steady-state model underestimates energy for protocols that wake often for very short checks. A protocol changes energy mostly by changing how long the node spends in each state.

4 · MAC I: contention

4.1What the MAC layer decides

  • Vocabulary: node (sensor, actuator, router, sink), link (direct relationship between two nearby nodes), path (sequence of links, multi-hop). Frame = MAC header + packet + trailer; packet = IP header + transport data; payload = application data. MAC protocols schedule and protect link-layer frames on a local channel.
  • The wireless channel is a shared medium: no private wire; a receiver can normally decode one useful signal at a time.
  • MAC decides channel access (transmit now, wait, back off?) and radio wake-up (listen, transmit, sleep?). Traditional MAC: avoid collisions, share fairly. WSN MAC: also minimize idle listening and unnecessary wake-ups.

The hard part: a sleeping receiver cannot hear a sender.

4.2Contention: CSMA/CA, backoff, ACKs

Contention-based MAC: no slot is reserved before traffic appears. Nodes try when they have data; randomness reduces simultaneous attempts; access time is not fully predictable.

  1. Wake radio, perform CCA (“does the channel look busy here?”).
  2. Idle → transmit. Busy → wait a random backoff.
  3. After failure → retry, possibly with a larger window.

Randomness prevents everyone retrying at the same instant. Collision avoidance reduces collisions; it does not eliminate them T5.

A missing ACK says something went wrong, not what: data lost, ACK lost, collision, receiver asleep, fading or interference.

Carrier sensing answers “what can I hear here?”, not “what is my receiver hearing over there?” It is conservative and local, not an oracle T4.

Why hidden terminals are common in WSNs: limited range, asymmetric links, different obstacles around nodes, nodes asleep during neighbour activity, and interference range can exceed communication range. Duty cycling reduces chances to learn who is active.

RTS/CTS: useful idea, poor fit for sensor radios

RTS → CTS → DATA → ACK. Hidden nodes that hear the CTS defer, which protects the receiver side better than sender-only CCA. Why it rarely ships in WSNs:

  1. Not in IEEE 802.15.4: no release defines it, so Zigbee, Wi-SUN and 6LoWPAN stacks inherit none.
  2. Tiny frames can’t pay for it: four exchanges per small frame; added experimentally, it only beat basic access on bandwidth efficiency once about 5 frames were concatenated.
  3. Broadcast has nobody to CTS: floods, beacons, routing updates, time sync.
  4. Interference outreaches decoding: a node too far to decode the CTS can still corrupt the data frame.

Also: sleeping nodes miss RTS/CTS, and RTS/CTS does nothing for exposed terminals; a CTS silences even more neighbours.

4.4Rendezvous and low-power listening

The rendezvous problem: the sender has a packet but does not know exactly when the sleeping receiver will wake.

Receiver idle duty cycle: D_idle ≈ T_check / T_wake 5 ms every 500 ms → 1 %

Low-Power Listening (LPL): the receiver periodically samples the channel. No activity → back to sleep quickly. Activity → stay awake for data. The sender must signal long enough to overlap at least one check. Preamble sampling: the wake-up signal (preamble) must cover the receiver wake-up interval plus a timing guard. Long preambles cost energy, latency, overhearing and channel occupation.

4.5B-MAC, X-MAC, ContikiMAC

B-MAC: long preamble + data

  • Receiver checks periodically (wake → CCA → sleep when idle). If it wakes during the preamble, it stays awake for the data. No global synchronization; duty cycle set by the check interval.
  • Strengths: simple, robust for low traffic, no clock sync, configurable, works with changing membership, a baseline for later designs.
  • The long preamble is the central cost: the sender transmits for about one check interval (T_TX ≈ T_preamble + T_data, since it cannot know when the receiver woke); the receiver may wait through the rest of the preamble; neighbours overhear and stay awake; the preamble occupies the channel; data waits; hidden terminals still collide.

“B-MAC’s preamble carries data.” No: the data follows the long preamble.

X-MAC: short addressed strobes + early ACK

  • Strobe, gap, strobe, gap… Each strobe names the destination. The awake destination sends an early ACK in a gap; the sender stops strobing and sends data immediately.
  • Non-targets decode an addressed strobe and go back to sleep: less overhearing (they still pay for one strobe).
  • Strengths: lower sender energy, less overhearing, shorter average delay. Limits: strobes and early ACKs can collide; hidden terminals remain; broadcast cannot rely on one early ACK.

ContikiMAC: repeated data frames

  • The sender repeats the complete data frame instead of a separate wake-up signal. The first complete copy received already carries the data. Efficiency depends on frame length, wake interval, inter-frame timing and ACK reliability.
  • Channel checks and fast sleep: multiple CCAs distinguish a valid packet train from noise; fast sleep returns the receiver to sleep when activity is irrelevant or invalid.
  • ACK-based termination: conceptually like X-MAC’s early stop, but the ACK confirms actual data delivery.
  • Phase lock: learn when a neighbour usually wakes and transmit near that time plus a guard. Without phase info, expected wait ≈ T_w / 2.

“ContikiMAC is just X-MAC.” No: repeated data frames, not short strobes; the stopping ACK confirms data, not wake-up.

Broadcast is expensive in asynchronous MAC: no single ACK can end it, and receivers wake at different times, so the sender may repeat for an entire wake-up interval. Network-wide cost: one sender’s wake-up signal can wake many neighbours.

4.6Receiver-initiated MAC: RI-MAC, A-MAC

Flip the rendezvous: the receiver wakes and announces availability with a beacon/probe; a sender with data listens for it and responds. No long sender preamble; the receiver controls availability. The sender may listen for up to one wake interval, and several senders can respond to the same beacon, so contention moves to the time after the beacon.

  • RI-MAC: receiver beacon → sender DATA → receiver ACK/beacon → optional next DATA.
  • A-MAC: probes are rendezvous opportunities that can carry receiver identity, timing and link-layer state; it separates “receiver is awake” from how senders contend.

  • 500 ms example: receiver checks 5 ms every 500 ms → idle duty 1 %; expected rendezvous ≈ 250 ms. B-MAC may need ≈ 500 ms of preamble; X-MAC/ContikiMAC can often stop earlier.

Big idea: schedule execution is not the same as schedule design. Scheduling trades spontaneity for predictability.

5.2TDMA vocabulary and cells

  • TDMA: time divided into fixed timeslots assigned to operations; nodes sleep in slots where they have no role. Simple as a concept, hard as a distributed scheduling problem. TDMA creates time resources; scheduling decides who uses them.
  • Timeslot: one opportunity to transmit, receive, ACK, contend or sleep. Slotframe: repeating collection of slots (a periodic calendar for radios). Slot offset: position inside the slotframe. A slot is a communication opportunity, not automatically a packet.
  • Dedicated cell: one TX–RX pair. Low collision probability, predictable service, stable latency, no backoff. Cost: wasted if no packet is queued; can become invalid after topology change.
  • Shared cell: several nodes may contend inside it. Useful for joining, Enhanced Beacons, routing control, negotiation, bursts. Brings back collisions, backoff, retries. “Scheduled opportunities, not collision-free guarantees.”
  • Spatial reuse: non-interfering links may share a slot; multiple channels add more reuse. The scheduler allocates time and frequency; over-conservative schedules waste capacity.

“TDMA means only one node transmits in the whole network.” No: spatial and frequency reuse exist. The goal is to separate conflicts, not silence the network.

5.3Inside a timeslot: guard time and energy

A slot must fit preparation, TX offset, DATA, RX/TX turnaround, ACK and timing uncertainty. The sender wakes, prepares, transmits at the TX offset, switches to RX, waits for the ACK. The receiver wakes before the expected arrival and listens within the guard time. Neither radio is on for the whole slot.

  • Guard time: how long a receiver listens around the expected arrival to tolerate clock error. Clocks drift; longer since last sync → longer guard → more listening energy. Frequent sync cuts error but costs communication T2.

Scheduled MAC converts time error into energy cost.

  • Duty cycle: first approximation active slots / total slots; e.g. 10-slot frame, 2 TX + 1 RX → 3/10 = 30 %. Refine with actual TX/RX/listen durations.
  • Waiting delay: one cell per frame = one service opportunity per frame. A packet arriving just after its cell waits almost a full frame; average ≈ half the inter-opportunity interval for uniform arrivals. More cells cut delay but cost resources and energy. Lower contention does not always mean lower latency.
  • Multi-hop cell order: A→B, then B→C, then C→D in the same frame pipelines a packet; downstream cells placed before upstream ones make it wait a frame per hop. Same number of cells, very different delay. “Scheduling is temporal routing support.”

5.6TSCH: Time-Slotted Channel Hopping

TSCH (IEEE 802.15.4 MAC mode, from 802.15.4e) combines time synchronization, scheduled cells, channel hopping, ACKs and link-layer retransmissions. TSCH executes a schedule; it does not prescribe the algorithm that computes it T5.

  • Cell = (slotOffset, channelOffset): a time–frequency opportunity, not merely a time slot. Multiple slotframes can coexist for traffic classes.
  • ASN (Absolute Slot Number): slots elapsed since the network began; +1 per slot. Used for time identification, channel calculation, security nonces and slotframe position. “The heartbeat of a TSCH network.” Losing sync can make a node transmit in the wrong slot.
physical channel = F[(ASN + channelOffset) mod N_c] F = hopping sequence, N_c = number of channels

  • Why hopping helps: frequency diversity against narrowband interference, frequency-selective fading, Wi-Fi overlap, persistent noise; a bad channel hits only some repetitions. It does not prevent broad-spectrum interference, poor schedules or sync failure. Robustness, not certainty.
  • Cell types: TX (wasted if no packet), RX (idle wake-up if nothing comes), dedicated (predictable, schedule overhead), shared (joining/control/bursts, collisions).
  • Slotframe length: short = low delay, fast retries, higher activity, little room; long = more cell positions and sleep, but longer waits and slower recovery; multiple slotframes = traffic classes. Longer is not automatically more efficient.
  • Synchronization and joining: new nodes scan for Enhanced Beacons carrying network and timing info, align ASN, join; nodes correct clocks from frame timing, ACK timing, beacons or a chosen time source.
  • Reliability vs determinism: time isolation, channel diversity, scheduled retries and controlled queue service reduce randomness. Determinism needs enough resources for data, routing, retries, joining and topology changes; poor schedules still overflow queues. “TSCH supplies tools; the schedule determines performance.” Practical schedules mix dedicated and shared cells.

5.7Orchestra and 6TiSCH

Orchestra: an autonomous TSCH scheduler (implemented in Contiki-NG) for dynamic IPv6/RPL networks. Computes local schedules from information already in the stack; no central scheduler, no per-link negotiation; adapts as RPL parents change.

  • Traffic planes: separate slotframes/rules for Enhanced Beacons, RPL control (shared rule), unicast data (per-neighbour cells), application traffic. One traffic type cannot dictate the whole schedule.
  • Hash-based assignment: both endpoints hash the same identifier → same cell, no negotiation. Hash collisions can put unrelated nodes in one cell; longer slotframes reduce collisions but raise latency. Hashing cannot promise uniqueness.
  • On a parent change: update RPL state, remove old parent cells, compute new ones, use them.

6.3Why IPv6 needs 6LoWPAN

  • Header mismatch: IPv6 base header 40 B + UDP 8 B = 48 B before any data; an 802.15.4 frame is at most 127 B including its own MAC header and FCS.
  • MTU mismatch: IPv6 requires every link to carry packets of at least 1280 B (minimum MTU). One frame is ten times smaller, so the adaptation layer must emulate a 1280-byte link with compression and fragmentation/reassembly.

Frame overhead varies: MAC control ≈ 3 B; addresses 2-byte short or 8-byte long (EUI-64) plus PAN IDs, ≈ 4–20 B; security header + MIC up to ≈ 21 B; FCS 2 B. Engineering goal: fit common packets in one frame, because fragments cost energy and reliability (§6.5).

6LoWPAN = IPv6 over Low-Power Wireless Personal Area Networks: an adaptation layer (“layer 2.5”) between IPv6 and the 802.15.4 MAC. Stack: Application · CoAP/UDP · IPv6 · 6LoWPAN · 802.15.4 MAC · 802.15.4 PHY. Applications still see the IPv6 model; a border router can expand packets back to normal IPv6.

6LoWPAN is not: a replacement for IPv6, a routing protocol (that is RPL or mesh-under), a permanent shortening of addresses (still 128 bits, just sent compressed), an application protocol (CoAP and MQTT-SN are), or a guarantee that every packet fits one frame.

6.5Fragmentation

When a (compressed) IPv6 packet still doesn’t fit, 6LoWPAN splits it into fragments, each with a fragment header, sent as separate frames. The receiver buffers them and delivers the packet only when all have arrived. The application created one datagram and never sees the fragments. A lost fragment makes the whole datagram unusable: there is no per-fragment recovery; after a reassembly timeout (up to 60 s) the buffer is discarded and the application must resend everything. This is link-level 6LoWPAN fragmentation, not IPv6’s end-to-end fragment header.

Avoid it: design the application for the link

  • Use compression well (link-local or context addresses, compact ports, default Hop Limit).
  • Prefer compact binary encodings (CBOR, SenML-CBOR) over verbose JSON/XML; limit metadata and batch sizes; send smaller observation batches.
  • Account for security overhead (DTLS/OSCORE add bytes) before deciding a message fits.
  • CoAP Block-Wise Transfer for large content: Block1 = large request body (client → server, e.g. firmware upload), Block2 = large response body (server → client, e.g. log download). Each block is an independent exchange, so a lost block is retried alone; 8 fragments at p = 0.9 succeed 43 % per attempt, while 8 blocks eventually all arrive with nothing wasted.

Overheating and irrigation-failure events need low latency and reliability. Average energy neutrality ignores timing and storage: the node must survive periods of no harvest with limited storage and charging losses (energy causality, not just averages). §3.7
Why do nodes near the sink tend to die first, and what does that do to “network lifetime”?
They forward traffic for many children, so their radios are busier. Depending on the definition (first node failure, sink unreachable, coverage), their death can end the network’s usefulness early; energy-aware routing balances load to protect critical relays. §3.6

MAC I · Week 4

What is CCA, and why can two hidden clients both decide the channel is idle? Where is the collision?
A short check at the sender of whether its local channel looks busy. Hidden clients A and C cannot hear each other, so each senses idle; their frames overlap at the common receiver B. §4.3
Why does random backoff help but not fully solve hidden terminals?
It randomizes attempt times, lowering the chance of simultaneous starts, but hidden nodes still have no awareness of each other’s transmissions, so long frames can still overlap at the receiver. §4.2
After a failed unicast, what can the sender infer from a missing ACK?
Only that the exchange failed: data lost, ACK lost, collision, receiver asleep, fading or interference are all possible. §4.2
Does RTS/CTS fix exposed terminals? Give two reasons it is rare in WSNs.
No; a CTS silences even more neighbours. Rare because 802.15.4 defines none; control frames cost too much for tiny data frames (gains appeared only around 5 concatenated frames); broadcast has no CTS; sleeping nodes miss it; interference range exceeds CTS decoding range. §4.3
Receiver checks 5 ms every 500 ms. Idle duty cycle? Expected rendezvous wait? Over 4 hops?
1 %; ≈ 250 ms per hop without phase info; ≈ 4 × 250 = 1 s over 4 hops. §4.7
What does B-MAC transmit while waiting for the receiver? What does X-MAC send instead, and what changes?
B-MAC: a long, unaddressed preamble covering the wake interval, then data. X-MAC: short addressed strobes; the destination answers with an early ACK, so the sender stops early and non-targets go back to sleep after one strobe (less overhearing). §4.5
How is ContikiMAC different from X-MAC?
It repeats the full data frame, not short strobes; the first complete copy delivers the data and the ACK confirms delivery. It adds multiple CCAs with fast sleep and phase lock. §4.5
Why is broadcast expensive under asynchronous duty cycling?
No single ACK can terminate it, and neighbours wake at different times, so the sender may repeat for a whole wake-up interval. §4.5
Why does phase lock not make rendezvous free in real networks?
Clock drift and stale phase information: the predicted wake time drifts, so guard intervals and re-learning after failures are needed. The MAC Bench assumes no drift, which makes it look cleaner. §4.5 Lab 4B
Increasing the wake interval from 50 to 500 ms: did energy disappear?
No. Receiver idle listening drops, but rendezvous delay and sender effort (longer preambles/strobes/repetitions or listening) rise. Rare monitoring traffic suits the long interval; urgent alarms may justify the short one. §4.7
In the wheat field, why did ground sensors become hidden terminals over the season while the drone still saw all of them?
The crop raised the ground-to-ground path-loss exponent from 1.85 to 5.93 (range at −75 dBm from 48 m to 8 m), while the ground-to-air path stayed clear. That is exactly the hidden-terminal geometry. §4.8
A utility reads 10 000 meters at :00, :15, :30, :45. Cheapest change to cut hidden-node collisions, and its cost?
Random jitter on report times within the interval. Cost: reads arrive spread out, so readings must be timestamped at the meter. §4.8

MAC II · Week 5

e1 conflicts with e2, e2 with e3; e1 and e3 do not conflict. Minimum slots? What could change it?
Two: e1 and e3 in slot 0, e2 in slot 1. Extra interference adds conflict edges and may require more slots; the result is only valid under the assumed interference model. §5.4
Communication graph vs conflict graph: what are the vertices and edges? List four conflict causes.
Communication graph: nodes and usable links. Conflict graph: transmissions, with an edge when two cannot share a resource. Causes: shared receiver, half-duplex, interference, ACK overlap. §5.4
F = [11, 15, 19, 23], cell channelOffset 2. Which physical channel at ASN 205? (illustrative numbers)
(205 + 2) mod 4 = 207 mod 4 = 3 → F[3] = 23. Next repetition with a 5-slot frame: ASN 210 → 212 mod 4 = 0 → 11. §5.6
Why does a longer time since synchronization cost energy in TSCH?
Clock error grows, so the receiver’s guard time must grow, and it listens longer per slot. Syncing more often costs control traffic instead. §5.3
A schedule is collision-free but B’s queue keeps growing. Explain using the slide-59 example.
A and C each send one packet per frame to B, but B has only one B→D cell, so arrivals (2) exceed service (1). Give B two forwarding cells. Conflict-free ≠ traffic-feasible. §5.9
Does TSCH define how cells are allocated? Who does in 6TiSCH?
No; TSCH executes a schedule. In 6TiSCH, a Scheduling Function (e.g. MSF) decides the policy, and 6P carries out neighbour transactions (ADD, DELETE, RELOCATE…). Orchestra is an alternative autonomous scheduler. §5.6 §5.7
Orchestra receiver-based vs sender-based rules: where does the cost appear?
Receiver-based: small state, but all children contend in the receiver’s cell (bottleneck). Sender-based: less child contention, but the receiver must listen in many RX cells (higher duty cycle). §5.7
Short vs long slotframes: which has lower delay and which more sleep? Is long always more efficient?
Short: more frequent opportunities, lower delay, higher activity. Long: more positions and sleep, longer waits and slower recovery. Not automatically more efficient. §5.6
Are WirelessHART and ISA100.11a interoperable because both use 802.15.4 radios?
No. They are different complete suites (IEC 62591, HART-oriented, network manager vs IEC 62734, IPv6-oriented, system manager with contracts). A shared radio family does not imply protocol interoperability. §5.8
Why can a predictable schedule be an attack surface?
Attackers can selectively jam critical cells, beacons or gateway RX slots, desynchronize nodes, replay timing/schedule messages, manipulate cells, or trigger excessive allocations. §5.9

Naming & 6LoWPAN · Week 6 (slides 1–31)

A node switches to a new RPL parent. Which changes: its name, its IPv6 address, or its route?
The route (and its next hop). The name stays the same, and the IPv6 address normally does too. §6.1
A packet crosses two relays. Which fields change at each hop?
Link-layer source and destination, and the IPv6 Hop Limit (64 → 63 → 62). The IPv6 destination and the resource name stay the same. §6.1
Does data-centric communication remove the need for addresses?
No. The topic or attributes name the data, but packets still go to an IPv6 endpoint (often a gateway), along a route, via next-hop radio addresses. §6.2
How many bytes are uncompressed IPv6 + UDP headers, and how small can 6LoWPAN make them?
40 + 8 = 48 B; best case 2 + 4 = 6 B, an 87.5 % reduction. §6.4
With an 80-byte effective frame, how much data fits uncompressed vs best-case compressed? Does a 50-byte message need fragments?
32 B vs 74 B. Uncompressed 98 B → 2 fragments; compressed 56 B → one frame. §6.4
An address is sent with 0 inline bits. Is the packet missing an address?
No. The receiver rebuilds all 128 bits from the link-local prefix or context and the 802.15.4 address (e.g. fe80::ff:fe00:25 from short address 0x0025). §6.4
What is the risk of stateful (context-based) compression?
Contexts are shared state that must be distributed and kept consistent; a wrong or stale context reconstructs the wrong address and decompression fails. §6.4
Can UDP port 5683 be compressed to 4 bits?
No. Only ports 0xF0B0–0xF0BF (61616–61631) compress to 4 bits each; 5683 goes inline (2 B) unless both ends agree on a compact port. §6.4
L = 200 B, M = 80, FRAG1 4 B, FRAGN 5 B. How many fragments? What about L = 225?
200: F₁ = 76, Fₙ = 75 → 1 + ceil(124/75) = 3 (aligned 72 + 72 + 56, still 3). 225: naive 3, but with 8-byte alignment 72 + 72 leaves 81 > 75 → 4. §6.5
Each fragment arrives with p = 0.9. Chance a 4-fragment datagram arrives complete? Why may reality be worse?
0.9⁴ ≈ 65.6 %. Losses are often correlated (bursts of interference/fading), which the independence model ignores. §6.5
A FRAGN header has offset 9. Where does its payload go, and why must non-final fragments be multiples of 8 bytes?
Byte 72 (8 × 9). Offsets count in 8-byte units, so every fragment before the last must end on an 8-byte boundary. §6.5
Why is CoAP Block-Wise Transfer better than relying on 8 fragments?
Each block is an independent exchange that fits a frame; a lost block is retried alone. With fragments, one loss discards the whole datagram (0.9⁸ ≈ 43 % per attempt). §6.5
Route-over vs mesh-under: which forwards fragments without reassembly, and which keeps IP tools working at every hop?
Mesh-under forwards fragments below IP without reassembly (IP sees one link). Route-over makes every radio hop an IP hop, so traceroute and IP routing see each node, but routers usually reassemble fragments. §6.6
List three things 6LoWPAN is not.
Not a replacement for IPv6, not a routing protocol, not a permanent address shortening, not an application protocol, not a guarantee that every packet fits one frame. §6.3
