Episode 00 · Start here

The two-minute version

No security background needed. Think of the internet’s padlock icon as an ID check.

  1. 1

    Websites carry ID cards

    When you visit your bank, its website shows your device a digital ID card, called a certificate, saying “I really am yourbank.com”.

  2. 2

    Only trusted offices issue them

    Your phone and computer come with a short list of trusted ID offices. Big offices delegate the daily work to branch offices, and an ID from any branch counts.

  3. 3

    Every office has a secret stamp

    Offices sign IDs with a secret stamp, a private key. A good stamp is a number so huge that nobody could guess it in billions of years.

  4. 4

    Eight stamps were guessable

    eMudhra, an Indian ID office, made eight branch stamps that were each just a number between 1 and 255. Anyone could find them in under a second.

  5. 5

    So fake IDs were possible

    With a copied stamp, a criminal could make a convincing fake ID for any website, and devices that still trusted those branches would believe it.

  6. 6

    Browsers reacted in hours, other software is slower

    Chrome, Firefox, Apple and Microsoft were told to reject the stamps within days. Many apps, servers and smart devices only learn about it when someone installs an update.

★ What should I do?

Everyone: install the latest updates for your browser, phone and computer. That’s enough for everyday browsing.

If you run servers, write software or manage devices: Episodes 6 and 7 show how to check whether your systems still trust the bad stamps.

Who’s who

eMudhra
The certificate authority (ID office) that made the weak keys.
Sectigo
Another certificate authority that had also vouched for the same eight branch offices, giving them a second route to trust.
Mozilla, Google, Apple, Microsoft
They run the “root programs”: the lists of ID offices that Firefox, Chrome, Apple devices and Windows trust.
“Wayne”
The independent researcher who found the problem and reported it on 17 October 2026.
Episode 01

Trust paths you can break

★ In plain words

Your device accepts an ID if it can trace a route from it back to an office on its trusted list. This tool shows every route a fake ID could take. Try switching things off: closing one route often isn’t enough, because two different offices vouched for the same stamps.

A TLS client trusts a server certificate only if it can build a chain from that certificate up to a root in its trust store. Roots sign intermediate CAs, intermediates sign the leaf certificates that sites present, and every intermediate inherits its root’s trust for any domain unless a constraint says otherwise. Guess an intermediate’s private key and you can mint a certificate for yourbank.com that chains to a trusted root.

Here the same eight weak keys sit in two certificates each: one issued by eMudhra’s emSign Root TLS (or CS) CA – G3, one cross-signed by Sectigo’s AAA Certificate Services. emSign Root TLS CA – G3 is a root on Windows and is itself cross-signed by emSign ECC Root CA – G3 everywhere else. That gives a forged leaf up to three ways home. Confirmed from the certificates and chains published with the disclosure

★ Key idea

Browsers moved within five hours because they own a push channel for distrust. Most other software has none, so a fix there means a package release, an image rebuild, or a firmware update.

Episode 03

The weak keys, from the real certificates

★ In plain words

A secret key should be a number so large it can’t be guessed, with more possibilities than there are atoms in the universe. These keys were numbers from 1 to 255. The console below takes the real certificates and simply tries 1, 2, 3… until it finds each key, in a fraction of a second.

These are ECDSA keys on the NIST P-384 curve. The private key is a scalar d, and the public key in the certificate is the point Q = d·G, where G is the curve’s fixed generator. Security rests on d being a uniformly random number of about 384 bits. Each of these eight keys is an integer below 256, so the private-key search space is at most 255 candidates: compute G, 2G, 3G, … until a point equals Q. How much entropy the generation process actually had is a separate question that the values alone don’t answer.

IntermediateUseSubject orgCheck itd

Every value above is recomputed in your browser from the embedded certificates: 8 eMudhra-issued certificates and 8 Sectigo cross-signs, as published with the disclosure. Confirmed The fingerprint links open each certificate on crt.sh, so you can check that the embedded bytes are the real ones.

Recover a key from its certificate

Pick an intermediate and which of its two certificates to attack. The console decodes the certificate’s DER, extracts Q, searches for d, then independently recomputes d·G by double-and-add and checks it against both coordinates of Q.

 KEYSEARCH.EXE · P-384

The search runs to completion first and is timed; the log then replays its steps slowly so you can watch. The time shown is the math, not the animation. The dashed button is a control: a freshly generated random key with no certificate, which the same search cannot crack.

Brute force over 2384 values is hopeless, and even the best generic attack on elliptic-curve discrete logs (Pollard’s rho) needs on the order of 2192 group operations. A correctly generated P-384 key is not the weak point in any realistic threat model. A badly generated one is.

Test any certificate

 SMALL-SCALAR TEST

Runs entirely in your browser; nothing is uploaded. Supports EC P-256 and P-384 keys. Passing only rules out tiny private keys. It says nothing else about key quality.

Episode 04

How a ceremony goes wrong

★ In plain words

Keys are made in a formal, witnessed procedure. According to eMudhra, a faulty script created extra, weak keys with similar names, and staff picked the wrong ones. A warning sign appeared a year earlier but was treated as a minor slip.

A key ceremony is the scripted, witnessed, audited procedure in which a CA generates keys inside a hardware security module (HSM) and produces certificate signing requests. eMudhra’s preliminary account in Mozilla bug 2083449 describes this chain of failures. CA-reported

  1. A faulty ceremony script created a second, weak key pair on the HSM alongside each properly generated one.
  2. Labels looked alike. Staff selected keys by human-readable label, and the weak pairs were picked when building the CSRs.
  3. The certificates were issued over the weak public keys, so the certified key and the key the CA later signed with were not the same.
  4. Human error at several steps, by eMudhra’s own account, let it pass review and audit.

Exactly how the weak keys came to exist inside the HSM environment, and why nothing in the ceremony caught them, is still being worked through publicly. Under investigation

★ The missed signal

If the CA kept signing CRLs with the good HSM key while the certificates carried the weak public keys, every CRL signature would fail to verify. Invalid CRL signatures from exactly these six TLS intermediates were observed in May–June 2025. Confirmed The June bug was closed as a process slip. eMudhra now links those failures to the same key mismatch. CA-reported If that holds, a pairwise-consistency check failed in production, publicly, 16 months before anyone looked closer.

eMudhra says only one of the eight (EM DV TLS CA – G3C) was ever put into production, that none issued end-entity certificates, that it has stopped issuing from G3, and that it will re-verify every ceremony it has run. About 30,000 customer certificates need to move to another hierarchy. CA-reported

Episode 05

Blast radius

★ In plain words

A copied stamp could be used to impersonate any website, to fake logins to some company systems, or to make malicious software look like it came from a trusted publisher. There’s no evidence anyone did, but it can’t be completely ruled out.

This is unusual among CA compromises. Normally someone steals a key, and you can reason about when it happened and who has it. Here nobody had to steal anything: the key was derivable from the public certificate from the day it was issued. Treat all eight keys as known to every attacker.

TLS impersonation

Six keys can sign a server certificate for any domain. An on-path attacker can intercept or modify HTTPS traffic for any client that accepts the chain.

Client auth and mTLS

All six TLS intermediates carry both the serverAuth and clientAuth EKUs, so forged client certificates are possible against servers that authenticate clients through these roots. Confirmed

Code signing

Two keys carry only the codeSigning EKU and chain to emSign Root CS CA – G3, a root in Microsoft’s store. Signed malware could look verified on systems that skip revocation checks.

Exposure window

About 17 months, April 2025 to October 2026. No exploitation has been confirmed. Under investigation

★ What CT proves, and what it doesn’t

No TLS certificate chaining to these intermediates was logged to Certificate Transparency before the block. Confirmed So normally configured clients that enforce CT for publicly trusted TLS, such as default Chrome, Firefox, Safari and Edge, could not have accepted a forged server certificate. That doesn’t cover browsers with CT enforcement turned off by policy, or curl, Python, Node.js, Go services and IoT firmware, which don’t check CT; for them the logs say nothing. Client-auth and code-signing certificates aren’t subject to CT at all.

Episode 06

Browsers vs. everything else

★ In plain words

Browsers have a fast lane for “don’t trust this” news and got it within hours. Most other software, from server tools to smart devices, has no fast lane and stays exposed until someone installs an update.

A browser rejecting one of these certificates now does so several ways at once. Most other TLS stacks have none of these defenses and rely on a static root bundle. You can reproduce each case in the trust path explorer.

Firefox · OneCRL / CRLite

Pushed intermediate blocklist

Delivered through remote settings, no update or restart. Firefox 158.0.1 and the ESRs carry it for installs that disable remote settings.

Chrome · CRLSets

Blocks by SPKI hash

Shipped 1 h 40 m after the report. Blocking the key rather than one certificate also covers the Sectigo cross-signs. Confirmed

All major browsers · CT

Transparency enforcement

A forged leaf has no SCTs, and Google says CT logs now reject certificates chaining to these CAs. Confirmed

Root programs

Distrust the root

Mozilla removed emSign ECC Root CA – G3 in NSS 3.131.1; Chrome is removing it too.

Chrome didn’t need to block the two code-signing keys: per the Chrome Root Program, its TLS verifier won’t build a server-certificate path through an intermediate restricted to code signing.

Where the gap is

  • Bundled CA files. curl, Python (certifi, pip, uv), Node.js and Rust (webpki-roots) carry their own copy of the Mozilla roots and usually don’t check revocation. In Scott Helme’s tests, curl, Python and Node.js on Linux and macOS accepted a forged certificate from EM DV TLS CA – G3B.
  • Static binaries. Go embeds its fallback roots and the new block at compile time. Deployed Go binaries keep the old behaviour until rebuilt with Go 1.27.3 or 1.26.10. The same goes for Electron apps.
  • Containers. A running image keeps the ca-certificates it was built with. Rebuild from a patched base.
  • macOS command-line tools. The built-in curl, git, python3 and openssl read /etc/ssl/cert.pem, which wasn’t updated, and don’t consult the OS block.
  • Embedded and IoT devices with frozen trust stores. These need the intermediates distrusted by hand, segmentation, and outbound restrictions.

Episode 07

Lab: why did it fail?

★ In plain words

Hands-on checks for people who run computers or servers. The main lesson: an error message isn’t automatically good news. What matters is why the connection failed.

The disclosure site runs test hosts that serve chains through the compromised intermediates. A failed connection is not automatically good news: it only helps if it failed for the right reason. A corporate proxy, an expired test certificate or a DNS problem all look like “error” too.

Task 5 · Write the check the ceremony was missing

python · weak_key_check.py
import sys
from cryptography import x509
from cryptography.hazmat.primitives.asymmetric import ec

cert = x509.load_pem_x509_certificate(open(sys.argv[1], "rb").read())
pub = cert.public_key().public_numbers()
curve = cert.public_key().curve

for d in range(1, 1 << 16):
    q = ec.derive_private_key(d, curve).public_key().public_numbers()
    if (q.x, q.y) == (pub.x, pub.y):
        print(f"WEAK KEY: d = {d}  ({cert.subject.rfc4514_string()})")
        break
else:
    print("no small scalar found")

Episode 08

Lessons and discussion

★ In plain words

The takeaways: double-check keys when they’re created, and make sure every system that relies on certificates can be updated quickly when something goes wrong.

For anyone who runs keys

  • Pairwise consistency, every time. Before publishing a certificate, sign a test value with the exact HSM key handle you will use and verify it with the certificate’s public key.
  • Select keys by fingerprint, not by label. Bind CSRs to a key identifier (SKI or public-key hash) that the ceremony record checks, not to a name a person reads off a screen.
  • Lint keys, not only certificates. Small-scalar, duplicate-key and known-weak-generator tests are cheap and belong in ceremony scripts and CA monitoring.
  • Treat “wrong key” symptoms as security events. An invalid CRL signature from a CA is a key-integrity question first and a process question second.

For anyone who relies on keys

  • Know every trust store you ship. OS bundle, language bundle, the copy inside a static binary, the one baked into a container image or firmware.
  • Block keys, not certificates. An SPKI block covers every certificate carrying the key, cross-signs included.
  • Have a distrust path faster than a release. Browsers have OneCRL and CRLSets; most backends have nothing between “root trusted” and “next package update.”
  • Enforce CT where you can. It turned an unknowable exposure into a provable non-event for normally configured browsers.

Discussion questions

Why did Chrome block only six of the eight intermediates?

The other two carry only the codeSigning EKU. Chrome’s TLS path builder won’t accept such an intermediate in a server chain, so those keys couldn’t produce a certificate Chrome would trust for HTTPS.

Mozilla removed emSign ECC Root CA – G3. Why can a client with that update still be at risk?

The Sectigo cross-signs chain the same eight keys to AAA Certificate Services, and on Windows emSign Root TLS CA – G3 is a root of its own. A client that trusts either, doesn’t check revocation, and lacks a key block can still build a valid path.

What lets us say normally configured browsers couldn’t have been attacked over TLS, and why doesn’t that extend to curl?

CT logs show no certificate under these intermediates before the block, and default browser configurations require CT proofs for publicly trusted TLS. curl and most libraries don’t check SCTs, so a forged certificate never logged anywhere would still be accepted. The claim also doesn’t cover client-auth or code-signing uses.

How could the June 2025 CRL incident have exposed this 16 months earlier?

Ask why the CRL signature didn’t verify against the certificate’s key. Comparing the certified public key with the HSM signing key would have shown a mismatch, and a small-scalar test on the certified key would have found d immediately.

Your curl connects to the AAA host but fails on the eMudhra host. What exactly is wrong with your trust store?

The ECC root (or the TLS-G3 path) is gone, but AAA Certificate Services is still trusted, and the client neither checks revocation nor blocks the weak keys’ SPKI.

Should a root program distrust a whole hierarchy for a mistake in eight intermediates that, by the CA’s account, issued no customer certificates?

Weigh 30,000 certificates to migrate against the signal that a CA’s ceremony, audits and incident response all missed a key that was guessable for 17 months, after a public warning sign.
